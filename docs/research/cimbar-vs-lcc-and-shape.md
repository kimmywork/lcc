# LCC vs Cimbar：差距、形状维度与增强路线

> **状态**：研究记录。后续实现采用了更简单的“线形态”方案（空白、`/`、`\`、`X`、`+`、`-`、`|`、`□`），代码见 `src/shapes.js`；本文中的 2×2/3×3 子格方案作为对照保留。
> **日期**：2026-11-09
> **范围**：Cimbar 对比、LCC 现状差距、把“形状”吸收为第二符号维度的可行性、设计草案、验证计划与风险。
> **结论先行**：LCC 当前是“单帧、分层、可打印/可数字”的参考编解码器；Cimbar 是面向“屏幕 → 摄像头高吞吐”的成熟系统。LCC 最大的差距是多帧/喷泉码、实时解码/跟踪、软判决/erasure 和实测基准；但**最值得先吸收的设计维度是形状**。形状比颜色更抗色偏，颜色 + 形状在同等 bit/模块下通常比继续堆颜色位宽更可靠。形状不是免费午餐：它需要子格分辨率、抗模糊形状集、联合分类、格式信令，以及 UEP/erasure 才能把“形状存活”转化为“数据存活”。

## 1. Cimbar 事实基线

Cimbar 是 sz3 的 color-icon-matrix barcode 研究项目，目标是用屏幕播放动画码、手机摄像头接收，达到约 **100 kb/s** 的传输率，单帧约 **10 KB**。

| 维度 | Cimbar 事实 |
| --- | --- |
| 符号 | 每个 tile 有 **16 个候选图标**，编码 **4 bit**；再加 **2–3 bit 颜色**，最多 **7 bit/tile** |
| tile 尺寸 | 典型 **8×8 像素**；一个 tile 是一个“小图标”，不是 LCC 意义下的一个纯色模块 |
| 形状解码 | 把 tile 与 16 个期望 tile 的 imagehash 比较，用 **Hamming 距离**选最近 |
| 颜色解码 | tile 平均颜色与颜色字典比较，选最近颜色 |
| 纠错 | Reed–Solomon + 交织；相邻 tile 不承载相邻数据，以容忍局部错误 |
| 多帧 | `libcimbar` 有基于喷泉码的数据封装；配合动画码做多帧累积 |
| 实测容量 | mode B（8×8、4 色、30/155 ECC、6 bit/tile）：**9300 B 原始 / 7500 B 默认纠错**；旧 mode 8C（8 色、7 bit）：10850 B / 8750 B |
| 工程实现 | Python 版是研究原型、较慢；C++ 的 `libcimbar` 做了大量优化和实测 |
| 规范 | 作者明确说“还没有 spec”，仍是 proof-of-concept |
| 作者自述限制 | 16 色“在当前颜色解码逻辑下似乎不可行”；4 色“完全合理”；8 色“在 dark mode 下可能”；符号集是手绘后筛选的，不是最优；RS 与“1–3 bit 翻转”的错误模式并不完全匹配；颜色校正主要交给相机；主要面向屏幕，不是纸 |

来源：

- <https://github.com/sz3/cimbar>
- <https://github.com/sz3/cimbar/blob/master/ABOUT.md>
- <https://github.com/sz3/libcimbar>

**关键观察**：Cimbar 的 4 bit 形状来自一个 8×8 tile；LCC 摄像头层的模块本身通常有 **12–20 px**（例如 L3c v7 是 20 px，L3d v10 是 16 px）。也就是说，LCC 的模块面积并不比 Cimbar 的 tile 小，**在 LCC 模块内部做 2×2 / 3×3 子格形状是可行的**，代价主要是解码复杂度和最小模块尺寸，而不是立刻损失容量。

## 2. LCC 现状基线

### 2.1 层级与色板

| 层 | 符号表 | bit/模块 | ECC | 最小 ΔE | 摄像头建议 |
| --- | --- | ---: | ---: | ---: | --- |
| L1 | 2 态黑白 | 1 | 20% | 100.0 | 首选 |
| L2a | 4 级等 L\* 灰 | 2 | 20% | 33.2 | 推荐 |
| L2b | 8 级等 L\* 灰 | 3 | 30% | 14.2 | 受控拍摄 |
| L3c | 16 色 max-min ΔE | 4 | 35% | 48.8 | 摄像头彩色首选 |
| L3d | 32 色 max-min ΔE | 5 | 40% | 35.7 | 受控拍摄 |
| L4e | 64 色 max-min ΔE | 6 | 40% | 25.0 | 清洁/数字/打印 |
| L4f | 256 色 max-min ΔE | 8 | 40% | 13.7 | 清洁/数字/打印 |

补充：用同一套 max-min 贪心色板算法，**4 色**的名义最小 ΔE 为 **100.0**（含白），**8 色**为 **80.2**（含白）；如果排除白色、限制 L\* < 70，则 4 色为 **117.3**，8 色为 **68.3**。这些是 sRGB/CIELAB 名义值，不是相机实测值，但趋势明确：**颜色位宽越高，最小 ΔE 下降得很快**。

### 2.2 几何、格式与解码

- 方形模块；`N = 21 + 4(v-1)`，`v=1..100`；最小模块 4 px。
- 3 个 `1:2:1:2:1` finder；`N≥25` 右下对齐图案；定时图案；BCH(15,5) 格式带。
- 校准枢纽：灰度层显示自身 4/8 级灰；彩色层使用 16 级参考灰 + 色板样本。
- 数据区按 Hilbert 顺序；RS(GF256) + 交织 + BCH 格式带 + CRC32；ECC 可选 L/M/Q/H + Boost ECC。
- 可逆邻差约束（rank 4/8/16，`maxDiff` 2/4/8，块 64）；摄像头建议关闭。
- 解码：Otsu/自适应阈值/闭运算多假设、finder 检测、单应、光照归一化、灰度多假设、彩色 3×4 仿射 + Lab 最近邻。
- 当前是**单帧硬判决**：一帧必须完整通过 RS + CRC；失败就整帧失败。

### 2.3 当前示例

| 文本 | 字节 | 层 | 版本/N | 模块 | ECC | 结果 |
| --- | ---: | --- | --- | ---: | --- | --- |
| Hello World! | 12 | L1 | v2 / 25 | 17 px | L | OK |
| The quick brown fox | 44 | L2a | v2 / 25 | 17 px | L | OK |
| Lorem ipsum | 446 | L3c | v7 / 45 | 20 px | Q | OK |
| 心经 | 944 | L3d | v10 / 57 | 16 px | H | OK |
| 金刚经 | 20406 | L4f | v45 / 197 | 10 px | H | OK |
| 心经摄像头模拟 | 944 | L3c | v11 / 61 | — | Q | OK，0 校正 |

## 3. 与 Cimbar 的差距

| 维度 | Cimbar | LCC 现状 | 差距 / 优先级 |
| --- | --- | --- | --- |
| 传输模型 | 多帧动画 + 喷泉码累积 | 单帧；RS 失败即整帧失败 | **P0** |
| 解码器 | C++/优化实现，面向视频流 | JS 参考实现，多假设重试 | **P0** |
| 时序 | 跨帧跟踪、对齐、融合 | 连续扫描只是重试，不融合 | **P0** |
| 纠错 | RS + 喷泉码；可跨帧重建 | RS + BCH + CRC；硬判决 | **P1** |
| 软判决 | 可用置信度/erasure | 符号硬判决；约束有 Viterbi，RS 仍是硬的 | **P1** |
| 符号维度 | **4 bit 形状 + 2–3 bit 颜色** | 只有颜色/灰度一维 | **P0/P1 设计缺口** |
| 颜色校准 | 相机颜色链路 + 屏幕场景调参 | 全局 3×4 仿射 + 局部光照 | **P1** |
| 实测基准 | 真实设备/光照/距离/帧率 | 主要是合成与少量模拟 | **P1** |
| 帧格式/安全 | 数据封装、喷泉码 | 基础帧 + CRC；压缩/加密/链式未做 | **P2** |
| 打印 | 主要面向屏幕 | 有打印路线但未实测 | **P2（LCC 差异化）** |
| 生态 | Android app、libcimbar | 参考实现 + Web demo | **P2** |
| 规范 | 作者明确说还没有 spec | 已有 LCC 规范 v0.2 | **LCC 优势** |

### 3.1 具体不足

**P0：没有多帧/喷泉码。** 现在一帧必须完整通过 RS + CRC；屏幕 → 摄像头场景的丢帧、模糊、反光会让整帧直接失败。Cimbar 的多帧喷泉码可以“收到足够多的任意帧就重建”，这是吞吐和鲁棒性的决定性差距。

**P0：没有实时解码器/时序跟踪。** 当前 Web 端是“拍一张、试多个预处理变体”，不是视频流跟踪。需要 ROI 跟踪、跨帧单应更新、时域平均、运动模糊处理，以及 WASM/Rust 或高度优化的 JS。

**P1：没有软判决 RS / erasure。** 颜色置信度低时，当前直接选最近色；应输出 top-k 候选/置信度，让 RS 使用 erasure 或软判决。

**P1：颜色校准还不够。** 全局 3×4 仿射 + finder/alignment 黑白云模型，对 L3c 够用；对 L3d/L4e 及广色域/护眼模式不够。缺 gamma、3D LUT、设备 profile、分区校准。

**P1：符号形态与空间同步。** Cimbar 的彩色 tile/icon 同时提供颜色判别和空间同步；LCC 是纯色方块。纯色方块在色渗、摩尔纹、模糊下容易混色；形状/子图案可以提供额外判别和同步信息。

**P1：缺 benchmark 矩阵。** 需要 ≥5 机型 × 3 光照 × 距离/角度 × 帧率，报告解码成功率、SER、goodput、延迟。没有这组数据，无法判断 L3c/L3d 的真实上限，也无法和 Cimbar 公平比较。

**P2：帧格式与安全层、打印链路、生态。** 压缩/加密/签名/多码链式/元数据尚未实现；打印链路未实测；没有通用扫描器。

### 3.2 LCC 的差异化优势

- 分层表：L1/L2a/L2b/L3c/L3d/L4e/L4f，鲁棒性 → 容量有明确档位。
- 可测的 max-min ΔE 色板：L3c 16 色 min ΔE 48.8，L3d 32 色 35.7。
- BCH 格式带 + 自定义 finder + 对齐图案 + 约束编码。
- 打印/数字/File Mode 路线：不是只做屏幕 → 摄像头。
- 参考实现透明、零依赖、可审计。

## 4. 为什么形状值得吸收

### 4.1 颜色和形状是两类不同的信道

色偏（白平衡、色温、屏幕色域、护眼模式、反光）主要改变 **颜色坐标**：RGB 通道增益、gamma、饱和度、混色。它会让色板在 Lab 空间里整体平移/缩放/压缩，**最近邻距离变小**，16 色、32 色会迅速混淆。

形状主要改变 **几何/占位**：哪些子格有墨、哪些没有。全局色偏、亮度变化、去饱和通常不会改变“有墨/无墨”的拓扑，只要局部对比度还在。因此：

- **形状适合承载粗粒度/高保护位**；
- **颜色适合承载细粒度/低保护位**；
- 两者组合，在同等 bit/模块下可以用更少的颜色换更大的颜色间距，并增加几何冗余。

Cimbar 的实践是直接证据：它的 4 bit 来自 16 个 tile 形状，颜色只承担 2–3 bit；作者明确说在当前颜色解码逻辑下 16 色不可行、4 色合理、8 色受控可能。**颜色位宽在真实相机链路上很早就饱和了，形状位宽还没有。**

### 4.2 同等 bit/模块下的对比

| 目标 bit/模块 | 纯颜色方案 | 最小 ΔE | 形状 + 颜色方案 | 颜色最小 ΔE | 形状最小 Hamming |
| ---: | --- | ---: | --- | ---: | ---: |
| 4 | L3c：16 色 | 48.8 | **L3s：4 形状 × 4 色** | **117.3** | 2 |
| 5 | L3d：32 色 | 35.7 | **L3t：8 形状 × 4 色** | **117.3** | 3（规则集）/ 4（max-min 集） |
| 6 | L4e：64 色 | 25.0 | **L4s：8 形状 × 8 色** | **68.3** | 3（规则集）/ 4（max-min 集） |
| 8 | L4f：256 色 | 13.7 | **L4u：16 形状 × 16 色**（未来） | ≥48.8（待优化） | ≥4（目标） |

> 注：形状层的颜色集排除白色（白作为背景），所以 4 色/8 色的最小 ΔE 与含白的 16 色/32 色不是完全同口径；但方向非常明确：**用形状换掉一部分颜色位，可以把颜色间距拉大一个量级，同时多一层几何冗余。**

### 4.3 形状还能带来“优雅降级”

纯颜色方案在严重色偏下是“全有或全无”：颜色判错，符号就错。形状 + 颜色可以设计成：

- 形状位单独可辨 → 即使颜色全错，形状位仍然活着；
- 把形状位和颜色位分到不同的 RS 块/比特面，颜色不可靠时标记为 erasure；
- 形状位用更强的保护，颜色位用较弱的保护（UEP）；
- 极端情况下退化为“形状 only”的低速率模式。

这正是纯颜色位宽做不到的。**但要注意：如果符号仍然要求颜色和形状同时正确，形状存活并不会自动变成数据存活；必须配合 UEP/erasure 或分层编码。**

### 4.4 合成 sanity check（方向性，不是 benchmark）

用 20 px 模块、2×2 半块形状、3×3 高斯模糊 1 次、σ=4 噪声、3000 次随机符号，比较：

- **L3c**：16 色纯色模块，整模块平均颜色 → Lab 最近邻；
- **L3s**：4 色（黑/蓝/绿/红，排除白）× 4 形状（上/下/左/右半块），子格占位判形状，墨色子格平均颜色判颜色。

| 条件 | L3c 符号错误率 | L3s 符号错误率 | L3s 形状错误率 | L3s 颜色错误率 |
| --- | ---: | ---: | ---: | ---: |
| clean | 0.0% | 0.0% | 0.0% | 0.0% |
| 暖色偏 | 6.3% | 0.0% | 0.0% | 0.0% |
| 冷色偏 | 6.3% | 0.0% | 0.0% | 0.0% |
| 去饱和 50% | 43.7% | 0.0% | 0.0% | 0.0% |
| 暖色偏 + 去饱和 + gamma 1.25 | 50.0% | 25.0% | **0.0%** | 25.0% |
| gamma 1.4 | 0.0% | 0.0% | 0.0% | 0.0% |

解释：

- 形状在所有这些条件下都 **0% 错误**；颜色在严重组合色偏下仍有 25% 错误。
- 因此 L3s 的联合符号错误率在温和色偏下明显优于 L3c；在严重色偏下仍受颜色位拖累。
- 这正好说明：**形状的价值需要编码层配合**。如果只做“形状 + 颜色联合硬判决”，严重色偏下颜色仍会拖垮符号；如果做 UEP/erasure，形状位可以独立救回来。
- 该实验没有透视、打印、真实相机链路，也没有完整校准枢纽；只用于判断方向，不能当作性能承诺。

## 5. 形状 + 颜色设计草案

### 5.1 符号模型

把一个数据模块定义为一个 **symbol tile**：

- tile 仍然占 **一个模块**（不改变 `N`、finder、对齐、格式带几何）；
- tile 内部划分为 `k × k` 个子格（subcell）；
- 形状 `s` 是一个 `k × k` 的二值占位掩码；
- 颜色 `c` 是墨色；未占位子格为白色背景；
- 符号表大小 `|S| × |C|`，`bit/模块 = log2(|S| × |C|)`。

关键约束：

1. **形状的墨覆盖率尽量一致**（例如都是 50%），否则平均颜色会被形状调制，颜色分类产生偏差。
2. **颜色集排除白色/近白色**，否则白色墨在白背景上不可见，形状占位失效。
3. 形状用**算法生成的二值掩码**，不用手绘图标；这样可复现、可测试、可写进规范。
4. 形状优先选**低频、连通、抗模糊**的图案；避免棋盘格、细对角线、孤立点。
5. 解码时颜色只从**占位子格**估计，形状从占位模式估计；最后做联合 refine。

### 5.2 形状集

#### S4：2×2，4 形状，50% 墨

推荐第一版，最简单、最抗模糊：

```
##   ..   #.   .#
..   ##   #.   .#
```

即上、下、左、右四个半块。任意两形状的最小 Hamming 距离为 **2**，墨覆盖率都是 50%。

- 优点：轴对齐、低频、渲染简单、颜色面积稳定。
- 缺点：只有 2 bit 形状；旋转/翻转靠 finder 定向解决。

#### S8：3×3，8 形状，规则集

推荐规则集（最小 Hamming **3**）：

```
###   ...   #..   ..#   #..   ..#   .#.   #.#
...   ...   #..   ..#   .#.   .#.   ###   ...
...   ###   #..   ..#   ..#   #..   .#.   #.#
```

即上排、下排、左列、右列、主对角、副对角、十字、四角。墨覆盖率 33%–56%，需要按形状的墨面积做颜色归一化。

也可以用 max-min 搜索得到最小 Hamming **4** 的 8 个 4 墨子格形状，但图案更不规则，抗模糊/打印稳定性需要实测比较。**第一版建议规则集优先，max-min 集作为对照。**

#### S16：4×4，16 形状，目标最小 Hamming ≥ 4

4×4 子格有更多自由度；建议用“最大最小 Hamming + 模糊鲁棒性 + 覆盖率平衡”的离线搜索生成，目标：

- 最小 Hamming ≥ 4；
- 每个形状墨覆盖率在 50% ± 12.5%；
- 高斯模糊后分类准确率 ≥ 99%（合成条件）；
- 旋转/翻转后不与另一形状混淆（在 finder 定向正确的前提下仍要求一定余量）。

S16 面向清洁/数字/打印，不建议作为第一版摄像头层。

### 5.3 颜色集

形状层的颜色集必须排除白色，并尽量排除近白色：

| 色数 | 建议 | 名义最小 ΔE | 备注 |
| ---: | --- | ---: | --- |
| 4 | 黑、蓝、绿、红 | **117.3** | L\* < 70；第一版 L3s |
| 8 | 黑、蓝、绿、红、品红、青、黄/棕、深青 | **68.3** | L\* < 70；L4s |
| 16 | 未来 | 48.8（含白，待重优化） | 形状层需要排除白后重新优化 |

颜色校准仍然使用**整模块满墨色块**（不是形状 tile），避免形状占位稀释颜色；形状 tile 只用于估计 PSF/占位阈值。

灰度形状层（L2s/L2t）同理：用 4 级灰墨，排除白；具体 L\* 级别需要离线优化，目标是保持“灰阶间距”和“与白背景的对比度”同时足够。

### 5.4 暂定层表

命名暂定；`s`/`t` 只是工作名，最终可以改成 `L3c-s` 之类。

| 层 | 形状集 | 颜色/灰度集 | 符号数 | bit/模块 | 目标 |
| --- | --- | --- | ---: | ---: | --- |
| **L2s** | S4 | 4 灰 | 16 | 4 | 灰度摄像头/打印 |
| **L2t** | S8 | 4 灰 | 32 | 5 | 灰度受控 |
| **L3s** | S4 | 4 色 | 16 | 4 | 彩色摄像头首选（对标 L3c） |
| **L3t** | S8 | 4 色 | 32 | 5 | 彩色受控（对标 L3d） |
| **L4s** | S8 | 8 色 | 64 | 6 | 清洁/打印（对标 L4e） |
| **L4t** | S16 | 8 色 | 128 | 7 | 数字/打印（介于 L4e/L4f） |
| **L4u**（未来） | S16 | 16 色 | 256 | 8 | 数字，对标 L4f |

现有 L1/L2a/L2b/L3c/L3d/L4e/L4f **保留**；形状层先作为并行选项，不强制替换。等实测证明 L3s 全面优于 L3c 后，再考虑把 L3s 设为摄像头彩色默认。

### 5.5 几何、容量与最小模块

- `N`、finder、对齐、格式带、Hilbert 顺序都不变；一个模块仍然是一个 tile。
- 形状层的容量 = `dataCount × log2(|S|×|C|)`；同版本下与同 bit/模块的纯颜色层基本相同，差异来自校准枢纽变大。
- 校准枢纽增加形状参考 tile 和满墨色块，数据模块会减少几个百分点，需要实测。
- 最小模块尺寸（初始建议）：

| 形状集 | 子格 | 摄像头最小模块 | 数字/打印最小模块 | 理由 |
| --- | ---: | ---: | ---: | --- |
| S4 | 2×2 | 8 px（子格 4 px） | 6 px（子格 3 px） | 半块形状，低频 |
| S8 | 3×3 | 12 px（子格 4 px） | 9 px（子格 3 px） | 3×3 需要更多子格像素 |
| S16 | 4×4 | 16 px（子格 4 px） | 12 px（子格 3 px） | 高密度，优先打印/数字 |

这意味着形状层在固定画布上会限制最大版本。例如 1024 画布、静区 2：

- S4 在 8 px 下 `N ≤ 124`，约 `v ≤ 26`；
- S8 在 12 px 下 `N ≤ 81`，约 `v ≤ 16`；
- S16 在 16 px 下 `N ≤ 60`，约 `v ≤ 10`。

但 LCC 的摄像头层本来就用较大模块（L3c v7 是 20 px），所以 **L3s 在常用摄像头档位的容量基本不变**（枢纽开销约几个百分点）；真正受限的是 L4t/L4u 这类高密度层，它们本来就面向清洁/数字/打印。

### 5.6 格式信令

当前格式带：

- 1 块（`N<25`）：mode 3 + ecc 2；
- 2 块（`25≤N<57`）：加 constraint 1 + palette 2 + seed 2；
- 3 块（`N≥57`）：加 seed 6 + flags 1。

形状层需要告诉解码器“这是形状模式，以及用哪个形状集”。可选方案：

**方案 A（推荐，最小改动）**：把 `mode=7` 作为 **shape escape**，把 2 bit `palette` 字段解释为 **shape layer ID**：

| mode | palette | 含义 |
| ---: | ---: | --- |
| 0–6 | 0/1 | 现有层，maxmin / harmony |
| 7 | 0 | **L3s**：S4 × 4 色，4 bit/模块 |
| 7 | 1 | **L3t**：S8 × 4 色，5 bit/模块 |
| 7 | 2 | **L4s**：S8 × 8 色，6 bit/模块 |
| 7 | 3 | **L4t**：S16 × 8 色，7 bit/模块 |

- 现有 `mode 0–6` 完全不变；不需要改格式带布局。
- 形状层要求 `N≥25`（2 块格式起有 `palette` 字段）；`N<25` 不支持形状。
- 解码器看到 `mode=7` 时，把 `palette` 解释为 shape layer ID；颜色数、形状集、bit/模块由规范表写死。
- harmony + 形状第一版不支持；未来需要时，可用 3 块格式的 `flags` bit 或扩展格式。
- 优点：只占用 1 个保留 mode 值，就能表达 4 个形状层；旧解码器看到 `mode=7` 会明确拒绝，不会误码。
- 缺点：`mode=7` 成为 escape，未来扩展要保留映射；规范必须写死 `(mode=7, palette) → symbol table`。

**方案 B**：`mode=7` + 3 块格式的 `flags` bit 作为扩展，给更多形状层/未来参数。第一版不需要。

**方案 C**：直接新增 layer ID。当前 mode 只有 3 bit，0–7，已用 0–6，只剩 1 个 ID，不够 4 个形状层；不推荐。

第一版建议 **方案 A**，同时把 3 块格式的 flags bit 留作未来扩展。

### 5.7 校准枢纽

形状层枢纽建议包含：

1. **16 级参考灰**：沿用现有亮度/白平衡锚点；
2. **形状参考 tile**：每个形状用黑色（或一个参考色）渲染，放在已知位置；用于估计 PSF/模糊核、子格对齐、占位阈值；
3. **满墨颜色块**：每个墨色一个整模块色块；用于颜色校准，不受形状占位影响；
4. **黑白端点**：枢纽边框角黑边白，沿用现有。

尺寸估算：

| 层 | 形状参考 | 颜色块 | 参考灰 | 枢纽大致 |
| --- | ---: | ---: | ---: | --- |
| L3s | 4 | 4 | 16 | 10×6 以内 |
| L3t | 8 | 4 | 16 | 12×8 以内 |
| L4s | 8 | 8 | 16 | 12×8 以内 |
| L4t | 16 | 8 | 16 | 14×10 以内 |

现有彩色层枢纽最大 22×18（L4f 256 色），所以形状层的枢纽尺寸不是瓶颈。

### 5.8 解码流程

```
检测 finder / 对齐 / 单应（沿用）
  → 读格式带，得到 layerId + palette + ecc + seed
  → 查符号表 (S, C, shapeSet, colorSet)
  → 对每个数据模块：
      在 k×k 子格中心采样
      光照归一化（沿用 illumination 模型）
      估计局部白/黑
      occupancy = ΔE(subcell, localWhite) > tau
      shape = argmin Hamming(occupancy, shapeMask)
      ink = occupancy 为真的子格
      color = argmin ΔE(mean(ink), colorSet)
      联合 refine：在 top-k (shape,color) 上最小化
        w_shape × shapeDistance + w_color × colorDistance
  → 符号流 → 约束/RS/去白化/CRC
```

要点：

- **占位判定不要只用亮度**。绿色、黄色等墨色可能很亮；用“与局部白的 ΔE”或“饱和度 + 亮度”更稳。
- 形状分类先用 Hamming，再用**模板匹配**：用形状参考 tile 估计模糊核，渲染候选形状模板，做归一化相关/最小平方误差。模糊下模板匹配比裸 Hamming 稳。
- 颜色只从占位子格估计；如果占位失败，回退整模块平均，但置信度降低。
- 输出 top-k 候选和代价，供后续 erasure/软判决 RS 使用。
- 失败回退：如果颜色置信度低，尝试“形状 only”假设；如果格式带/RS 支持，走低速率分层解码。

### 5.9 编码与 UEP

第一版：

- 符号索引 `sym = shape * C + color`；
- 形状位作为高位，颜色位作为低位；
- 沿用现有 RS/交织/白化/CRC，先验证基线。

第二版（关键）：

- 把形状位和颜色位拆成两个比特面/两个 RS 块组；
- 形状位用更强 ECC（或更多重复/更低码率），颜色位用较弱 ECC；
- 颜色置信度低时，把颜色位标记为 erasure；
- 这样严重色偏下可以“形状位先活”，而不是整符号失败。

第三版：

- 软判决/erasure RS；
- 与多帧/喷泉码结合：形状位和颜色位可以按不同优先级进入喷泉码。

**没有 UEP/erasure，形状的鲁棒性只能体现在“温和色偏下联合符号更稳”，不能体现在“严重色偏下仍能恢复数据”。**

### 5.10 渲染与输出

- PNG：每个子格画成矩形；源图不做抗锯齿；模块边界清晰。
- SVG：子格矩形或 path；`shape-rendering="crispEdges"`。
- 打印：最小子格 3–4 px（按目标 DPI 换算）；优先 S4 半块形状，避免细对角/棋盘。
- Web 统计面板增加：形状集、子格尺寸、最小 Hamming、颜色最小 ΔE、平均墨覆盖率、估计容量。
- 预览：显示形状 + 颜色分解图，方便调试。

### 5.11 验证计划与指标

**合成实验**（先做，成本低）：

- 色偏：暖/冷白平衡、色温、饱和度下降、gamma、通道增益；
- 模糊：高斯/运动模糊、不同 PSF；
- 噪声、压缩伪影、摩尔纹；
- 模块尺寸：8/12/16/20/24 px；
- 指标：SER、BER、shape-only SER、color-only SER、joint SER、RS 校正数、解码成功率。

**相机实验**：

- ≥5 机型 × 3 光照（室内/室外/屏幕反光）× 距离/角度 × 帧率；
- 指标：解码成功率、SER、goodput（B/s）、延迟、CPU/功耗；
- 对比：L3c vs L3s、L3d vs L3t、L4e vs L4s，在**同 bit/模块、同模块尺寸、同画布容量**三种口径下分别比较。

**打印实验**：

- 打印机/纸张/半色调/扫描仪或手机；
- 指标：SER、最小可读子格、颜色漂移、逐机校准效果；
- 优先 L2s/L3s 的打印档。

**消融**：

- shape-only、color-only、joint；
- 有/无校准枢纽；
- 有/无 UEP/erasure；
- 规则形状集 vs max-min 形状集。

**通过标准（建议）**：

- 同等 bit/模块、同等模块尺寸下，L3s 在色偏/去饱和条件的 SER 不高于 L3c；
- 形状 only 在 20 px 模块、温和模糊下 SER ≤ 1%；
- 清洁图像无回归；
- 格式带/旧层解码保持兼容。

### 5.12 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 子格分辨率不足 | 形状判错，容量下降 | 最小模块约束；S4 优先；按画布动态选版本 |
| 模糊/失焦/运动模糊 | 形状高频细节丢失 | 低频形状；模板匹配；PSF 估计；S4 半块 |
| 颜色渗色/相邻模块干扰 | 占位和颜色都受影响 | 子格中心采样；局部白估计；模块间保护；联合解码 |
| 形状-颜色耦合 | 平均颜色被形状调制 | 等墨覆盖率形状；颜色只用占位子格；满墨色块校准 |
| 旋转/透视 | 形状定向错误 | finder/对齐定向；形状集旋转余量；单应 |
| 格式信令不足 | 无法区分形状集 | `mode=7` escape + palette ID（方案 A）；规范写死映射；保留 flags |
| 校准枢纽变大 | 数据容量下降 | 紧凑枢纽；按层裁剪参考 tile；实测开销 |
| 打印套准/半色调 | 子格边界糊 | 打印最小子格；S4；逐机校准；避免细对角 |
| 复杂度/测试量 | 实现和维护成本 | 先做 L3s 离线原型；分阶段；合成 + 相机 + 打印 |
| 标准化困难 | 形状集难冻结 | 算法生成掩码；版本化形状集 ID；测试向量 |
| 合成实验过度乐观 | 误判方向 | 明确标注 synthetic；以相机/打印实测为准 |

| 阶段 | 内容 | 退出标准 |
| --- | --- | --- |
| **0. 本研究** | 记录差距、形状方向、设计草案 | 本文档评审通过 |

### 5.14 待决策问题

1. 形状层是**并行层**（L3s/L3t/...）还是**修饰符**（L3c + shape flag）？本文倾向并行层，便于规范和解码器查表。
2. S8 用规则集（min Hamming 3）还是 max-min 集（min Hamming 4）？需要模糊/打印实测。
3. 最小子格 3 px 还是 4 px？摄像头/打印分开定。
4. 格式信令用 `mode=7` escape + palette ID（方案 A）还是 flags（方案 B）？本文倾向 A。
5. 颜色集排除白后，4 色/8 色具体取哪些？需要按设备色域再优化。
6. L2s/L2t 的灰阶级别如何选？排除白后如何保持与白背景的对比度？
7. 形状优先还是喷泉码优先？本文建议先做形状离线原型（成本低、和现有单帧管线兼容），但多帧/喷泉码仍是 P0 吞吐差距。
8. 先做屏幕还是先做打印？LCC 的差异化在打印，但形状的摄像头验证更容易先做。

## 6. 结论

1. **Cimbar 的核心优势不是“颜色更多”，而是“形状 4 bit + 颜色 2–3 bit + 多帧喷泉码 + 优化解码器”。** LCC 在单帧容量/色板上已经不弱，但在传输模型、时序、软判决和实测基准上差距明显。
2. **形状是 LCC 最值得先吸收的符号维度。** 它和颜色近似正交；在同等 bit/模块下，用形状换掉一部分颜色位可以显著拉大颜色间距，并增加几何冗余；在色偏/去饱和下，形状通常比颜色更晚失效。
3. **形状不是免费午餐。** 它需要子格分辨率、抗模糊形状集、联合分类、校准枢纽、格式信令；如果没有 UEP/erasure，严重色偏下颜色位仍会拖垮联合符号。
4. **建议第一步做 L3s 离线原型**：4 形状 × 4 色 = 16 符号，4 bit/模块，与 L3c 同版本、同模块尺寸对比。这是最低成本、最高信息量的实验；通过后再进入格式集成，然后再做 UEP、多帧/喷泉码和 benchmark 矩阵。

## 附录 C：合成 sanity check 方法

- 模块 20×20 px；L3c 整模块纯色；L3s 为 2×2 子格，四个半块形状，50% 墨。
